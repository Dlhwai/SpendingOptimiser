01 / recommended defaults

Small operational footprint, explicit domain logic

Python + FastAPI

Python is a good fit for parsing and financial rule tests. FastAPI supplies local HTTP endpoints; Pydantic validates imported data and rule configuration.

A CLI entry point starts the app. Package as a standalone executable only after the core behavior is stable.

SQLite

One local database for messages, transactions, rules, and sync state. SQLAlchemy + Alembic provide persistence and migrations.

No hosted database, Redis, or external job queue for a single-user MVP. Serialize writes and maintain tested backups.

Jinja2 + HTMX

A server-rendered browser dashboard gives you refresh, corrections, and monthly summaries without a separate frontend build pipeline.

React is reasonable if rich interactive planning becomes central. It is not necessary just to get a refresh button.

Tradeoff: Python simplifies the data-heavy core, but native executable packaging and OS credential storage need platform testing. If a single TypeScript stack is your preference, the same module boundaries still apply.

02 / system boundary

How does a transaction become a useful decision?

New requirement / reusable card onboarding

Tell the chatbot a card name, not its entire rulebook

The chatbot is a thin client of a reusable card-catalog and research API. A card name starts a durable research job. AI fills a structured draft from public sources; deterministic validation and an approval step control what becomes an active financial rule.

1 / Identify

Resolve the exact product

Normalize aliases and resolve issuer, country, product, and payment-network variant. Default to Singapore for this project; ask a focused question if the name matches multiple cards.

A shared card product is separate from the user's card instance, approval date, statement cycle, and promotion enrollments.

2 / Discover

Find authoritative sources

Search official issuer pages, then follow card-specific terms, general reward exclusions, reward-program/redemption terms, and relevant campaign documents. Use official program partners when linked by the issuer.

MoneySmart/Singsaver documents govern their own campaigns, not the card's ordinary earning rules. Marketing summaries alone are insufficient.

3 / Retrieve

Preserve the evidence

Fetch HTML and PDF documents; extract text, tables, and footnotes, with OCR when needed. Retain the original source, URL, retrieval time, content hash, and stated effective dates.

Blocked, unreadable, expired, and future-effective documents are explicit outcomes, not successful current-term extraction.

4 / Extract

Fill a typed rule draft

A provider-independent LLM adapter extracts earning units, rates, thresholds, eligibility, exclusions, shared caps, date basis, rounding, and redemption conditions into the rule schema.

Every proposed field has a value, exact source citation, and evidence status. Missing is not zero or false. Preserve conflicts rather than silently choosing a source.

5 / Validate

Check semantics and support

Validate types, units, periods, cap scopes, and required evidence. Run independent fixtures and boundary tests for thresholds, caps, refunds, and rounding. Show missing, conflicting, and unsupported conditions.

An LLM's confidence is not validation. Unsupported formulas need a tested engine extension; do not generate and execute arbitrary code from retrieved documents.

6 / Activate

Review and publish a version

Present a concise sourced summary and unresolved questions. Approval publishes an immutable, effective-dated profile. The reward engine evaluates that profile, never the research chat transcript.

Incomplete cards can still track spending, but affected rewards remain unverified. A new card using supported rule types needs configuration, not a new calculator.

Reusable operations

research_card starts or resumes research; get_card_draft returns sources and gaps; activate_card publishes an approved version; refresh_card_terms proposes later changes.

Expose the same application operations to the built-in chat, CLI, or a future external chatbot. Keep the core independent of a chat vendor or model provider.

Updates without silent history changes

Periodically check known sources for changes. A new document creates a candidate version and semantic diff, not an automatic overwrite. Preserve historical versions and distinguish retrieval date from effective date.

Public terms cannot reveal personal approval dates, signup channels, new-to-bank eligibility, or whether the user enrolled. Ask only for the missing personal facts.

Research isolation: public card-document research does not need Gmail messages or financial transactions. Treat fetched text as untrusted data, not agent instructions; restrict fetching to safe public destinations, enforce time/size limits, and gate activation through initial approval or the configured verified-update policy. This remains one local application, with a reusable internal service boundary rather than a new deployed microservice.

New requirement / automated format adaptation

A changed bank email should trigger adaptation, not a dead end

Use deterministic extraction for recognized templates, constrained AI extraction for unknown or drifting formats, and a validated template registry to make future messages inexpensive and repeatable. Routine format changes should not require handwritten parser updates.

1 / Detect

Recognize changes, including silent ones

Classify messages from approved bank sources, check authentication/forwarding context, and fingerprint normalized structure and field-label anchors. Mask varying amounts, dates, and identifiers before matching a template.

A parser returning a number is not enough. Trigger fallback on missing fields, unexpected anchors, changed structure, or suspicious semantic changes, even when parsing technically succeeds.

2 / Extract

Read the unfamiliar notification

A restricted extraction model proposes typed events and exact evidence spans for amount, currency, merchant, account/card mapping, event type, and available dates. Keep notification time distinct from transaction and posting time.

Recognize refunds, reversals, declined transactions, balances, OTPs, and marketing. Do not assume every bank message represents a completed purchase, or guess absent currency/MCC information.

3 / Validate

Decide what can enter the ledger

Check schema, source spans, amount/date parsing, field-label meaning, currency, known accounts, and transaction identity. Automatically accept unambiguous extractions from trusted sources only when the configured validation gate passes.

Model confidence alone is never the gate. Missing, conflicting, or ambiguous records remain provisional and visible for review; do not quietly drop them or present them as confirmed spending.

4 / Learn

Propose a reusable extraction template

Derive a bounded declarative extraction specification, not arbitrary executable parser code. Replay against verified historical fixtures and multiple new examples; compare field evidence and run a shadow version before promotion.

Auto-promote only when qualification checks pass. Unresolved semantic choices need confirmation or independent records; model-generated expected answers alone are not a trustworthy test oracle.

5 / Recover

Reprocess without double counting

Version templates and extraction results, retain evidence, and replay affected messages using stable source identity. Preserve manual corrections and pending/posted links, then rebuild affected financial projections.

Keep prior template versions for rollback and historical replay. Record how many messages were adapted, remain unresolved, or failed; expose last successful processing and next actions.

Separate privacy boundary

Emails are private input, not public terms

Prefer local extraction; sending transaction content to an external model requires explicit opt-in. Minimize disclosed content and mask personal identifiers, while acknowledging that merchants, amounts, and dates remain sensitive.

Email content is untrusted data, never model instructions. No tool execution, arbitrary network access, or generated-code execution from email. Bound model calls and cache qualified templates.

Two independent learning loops: card onboarding learns public reward policies; adaptive ingestion learns private transaction formats. Both produce versioned, validated configuration for the same deterministic core. Changing the presentation can be handled automatically; facts absent from the notification still require another reliable source.

New requirement / daily MileLion monitoring

News discovers a change. Governing terms verify it.

Check MileLion once daily, identify news affecting tracked cards and reward programs, and reuse the card-research pipeline to verify changes. Automatically publish supported, unambiguous updates under a configured policy; unresolved changes go to review.

Verified source: MileLion's blog advertises https://milelion.com/feed/. The live RSS response inspected during planning contained 10 items and supplied ETag and Last-Modified headers. These are observed feed properties, not a guarantee of complete historical coverage.

1. Discover and match

Poll the RSS feed with conditional HTTP requests, persist the last successful watermark, and deduplicate by article identity and content revision. Match product aliases, issuers, and reward programs, including bank-wide changes that do not name a specific card.

Start with Maybank Rewards XL, DBS yuu Visa, and Trust Freedom. Use archive/sitemap catch-up when the previous watermark is outside the feed's retained items; expose coverage gaps if catch-up fails. Respect robots rules and avoid disallowed site-search routes.

2. Verify and compare

Extract the article's claims and linked evidence, then fetch applicable issuer/program documents. Compare normalized rules for earning, minimum spend, caps/exclusions, redemption, and campaign dates. Record published, retrieved, and effective dates separately.

MileLion is an editorial discovery source, not a governing reward policy. Blog-only claims, conflicting terms, unreadable evidence, and unclear effective dates cannot update active financial rules. Also recheck tracked official documents directly; RSS cannot catch every change.

3. Publish a verified version

Auto-apply only when the standing update policy permits it, every changed financial field has governing evidence, the engine supports the conditions, effective dates are established, and validation/regression checks pass. Otherwise preserve the candidate for review.

Publish a new immutable version rather than overwrite old rules. Schedule future-effective changes for the right date; preserve calculation history and flag retrospective corrections. Never auto-add cards, enroll in campaigns, or invent personal eligibility.

4. Report and recover

Show verified changes, pending reviews, failures/coverage gaps, last successful check, and next run. A successful empty run explicitly says “0 relevant updates”; a failed fetch must not report “no changes.”

Schedule once daily in Asia/Singapore, with configurable time and manual “Check updates now.” Use a durable, idempotent job and catch up after downtime. A local executable cannot run while the machine/app is off; unattended operation needs a suitable scheduler or always-on host.

This is a third automation loop beside card onboarding and email-format adaptation. Reuse the existing source-document store, typed drafts, validation engine, and version publisher instead of creating another calculator or deployment.

03 / key components

Ten components with clear responsibilities

1. Gmail ingestion

OAuth, configured labels/senders, initial backfill, and incremental history. Persist message IDs and source content before moving the checkpoint. Recover from expired history with a bounded rescan.

A label limits what the app processes; it does not restrict the Gmail read-only permission to that label.

2. Adaptive transaction extraction

Versioned bank/template registry, structural drift detection, constrained AI fallback, evidence-based validation, candidate-template learning, regression checks, promotion, and replay.

Known templates stay deterministic. Unknown formats trigger automated adaptation; only ambiguous or unsafe results need review. Never silently turn uncertain extraction into a confirmed financial record.

3. Canonical ledger + reconciliation

Accounts and card instances; purchases, income, transfers, repayments, fees, refunds, and reversals. Link multiple source records to one transaction and distinguish pending from posted.

Manual entries/corrections are essential. Add statement or CSV import for completeness; an email alert is often only an authorization.

4. Reward-rule engine

Versioned card rules calculate minimum-spend progress, eligible spend, base/bonus rewards in native program units, category caps, and rounding. Support calendar months and card-specific statement periods. Keep point-to-mile/cashback redemption rules and optional value estimates separate from earning.

Return a breakdown and reason for each estimate. Missing MCC or payment-channel evidence means provisional eligibility, not an invented classification.

5. Promotion tracker

Bank and MoneySmart/Singsaver campaigns are separate from ordinary card rewards. Track enrollment, application/approval dates, new-to-bank/card declarations, spend windows, conditions, and reward claims.

Model bank and aggregator campaigns separately, including explicit stacking rules. Qualified, claim pending, and reward received are different states.

6. Cash-flow + budget engine

Salary and incoming transfers, spending per card, real account cash movement, planned bills, savings allocation, and a remaining daily allowance.

Budget card purchases when made. Count repayment as a transfer, not another expense. Own-account transfers are not income.

7. Dashboard + local API

Monthly overview, transaction review, card/promotion progress, sync status, and refresh. Show source coverage, last successful sync, and unreviewed records alongside totals.

Recommendations can follow once the ledger and rules are trusted. First explain what happened and what remains to meet a threshold.

8. Local runtime + persistence

CLI entry point, SQLite migrations, durable sync-run state, redacted logs, credential storage, backups, and recovery. Optional periodic polling uses the same refresh pipeline.

Bind to loopback by default, protect mutation endpoints, and keep OAuth refresh tokens in the OS credential store, not source files.

9. Card catalog + AI onboarding

Chat-driven product discovery, authoritative source retrieval, evidence-backed term extraction, gap detection, rule validation, and approved profile publication. Existing profiles are reusable across integrations.

The onboarding API produces versioned rules; it never directly modifies transactions or decides rewards at runtime. See the onboarding workflow above.

10. Daily news + policy refresh

MileLion RSS discovery, card/issuer/program relevance matching, archive catch-up, official-term verification, semantic rule diffs, policy-gated publication, and a daily change digest.

Keep editorial claims distinct from governing evidence. Persist article revisions, source authority, update candidates, decisions, and job status. No blog-only change enters active reward calculations.

04 / repository organization

Keep business rules independent of Gmail and the UI

Proposed package root: src/expense_tracker/. Start with small modules; create subpackages only as they grow. No framework-specific objects inside the domain.

Application package

  • src/expense_tracker/domain/Money, accounts, transactions, card-profile/rule schemas, reward evaluation, promotion conditions, and budget calculations. Pure, deterministic business logic.
  • src/expense_tracker/application/Transaction refresh/adaptation, card onboarding, daily news/term checks, draft validation and publication policy, reconciliation, and reporting. Reusable from web, CLI, and chatbot clients.
  • src/expense_tracker/infrastructure/Gmail, extraction templates, RSS/HTTP caching and archive discovery, durable scheduling, document extraction, separately permissioned research/private-extraction models, SQLite, and credential storage.
  • src/expense_tracker/web/FastAPI routes, dashboard templates, and static assets. Delegates to application use cases.
  • src/expense_tracker/cli.pyStarts the local service; shared application commands support refresh, status, and export without duplicating logic.

Rules, tests, and operations

  • rules/cards/ + rules/promotions/Validated YAML or JSON: effective dates, conditions, periods, caps, reward formulas, and source references.
  • tests/unit/ + tests/integration/Reward boundaries, transfer treatment, idempotent refresh, format drift, fallback validation, template qualification/rollback, checkpoint recovery, and replay.
  • tests/fixtures/emails/Sanitized old/new bank templates, independently verified expected events, ambiguous multi-amount messages, refunds, non-transactions, and malicious instruction text. Never commit actual account details or tokens.
  • tests/fixtures/news/RSS duplicates/revisions, feed-window gaps, editorial-only claims, conflicting official evidence, future-effective rules, fetch failures, and idempotent policy-approved publication.
  • migrations/ + docs/Schema evolution, rule assumptions, parser coverage, reconciliation procedures, and backup/restore instructions.

Dependency direction: Web/CLI call application use cases; application uses domain rules and adapter interfaces; infrastructure implements those interfaces. Reward evaluation must be testable without Gmail, HTTP, or a database.

05 / minimum durable records

Store evidence and decisions, not just monthly totals

Accounts + transactions

Account/card identity, transaction lifecycle, source links, original and billed money, and transaction/posting dates. Pair internal transfers and repayments so reports do not double count them.

Sources + extraction history

Stable mailbox/message identity, retained evidence, template fingerprints and versions, field-level extraction evidence, and validation outcomes. Sync runs and template candidates retain their status, quality checks, and recovery history.

Card catalog + rule evidence

Card products, source-document snapshots, extracted-field evidence, draft status, and approved rule versions. Evaluations record the effective policy, period, reward breakdown, and uncertainty. Separate estimates from reward receipts.

Enrollments + budget periods

Campaign enrollment and claim milestones; personal budget, income assumptions, commitments, savings targets, and opening balances when reporting available cash.

Store money in integer minor units appropriate to each currency, with Decimal arithmetic for FX and rounding, never binary floats. Monthly totals are rebuildable projections. Retain correction history and rule versions so changing a parser or card policy does not silently rewrite the explanation for past results.

06 / financial correctness

The boundaries that prevent misleading numbers

Separate the three views

  • Budget spending: a $100 card purchase consumes $100 of the spending budget.
  • Bank cash flow: money leaves the bank when the card is repaid, not when the purchase is authorized.
  • Reward spend: the same $100 may contribute differently to a minimum-spend requirement and to a bonus category.

This separation is more important than the choice of frontend framework.

Make the daily allowance explicit

Daily allowance = remaining unallocated monthly budget / remaining calendar days.

Set a discretionary budget after savings and fixed-bill reserves. Subtract net discretionary spending and new discretionary commitments not already recorded. Pay reserved bills from their reserves, not from the discretionary budget a second time; release a commitment's reservation when its payment is recorded.

Count today if its budget is still available. Show an overspend warning when negative. This is a planning allowance, not a bank-balance guarantee; future salary and rewards stay forecast until received.

Rules need more than a percentage

Separate predicates for minimum spend and bonus eligibility. Handle merchant/MCC, online or contactless channel, currency, exclusions, caps, transaction versus posting date, refund clawbacks, and per-transaction or period-level rounding.

Validate declarative rules with a bounded set of supported operators. Use small tested code handlers for genuinely complex formulas, never arbitrary code execution from a rule file.

Emails are an incomplete source

Not every transfer, salary payment, settlement, refund, or MCC appears in Gmail. Missing evidence should be visible, with manual enrichment and eventual statement reconciliation.

Exact message IDs prevent repeat imports. Bank transaction IDs can link duplicates; fuzzy matches are review suggestions, since two identical purchases may be legitimate.

Trust and privacy: OAuth only; no banking passwords. Encrypt tokens through the OS credential store, use device/disk encryption for the database, redact logs, and make raw-email retention configurable. Treat email HTML and links as untrusted: sanitize displayed content and never execute embedded instructions. Test backup restoration and preserve audit history.

07 / end-to-end behavior

What happens when you press Refresh?

  1. Create or reuse the active sync run for the mailbox; keep the dashboard responsive.
  2. Fetch new messages, save source records idempotently, and commit the checkpoint only after the covered messages are durable.
  3. Match templates and validate field anchors. Unknown or changed formats trigger constrained extraction and template qualification; accept validated results and keep ambiguous records visible for review.
  4. Upsert or link transactions using reliable identity evidence; preserve user corrections and pending/posted relationships.
  5. Recompute affected budgets, reward periods, and promotion progress. Keep estimates distinct from confirmed amounts.
  6. Show last success, imported/duplicate/review/failed counts, source coverage, and next actions. A failed import must not look like zero spending.

Use a durable jobs table with a single local worker and per-mailbox lock. Restart unfinished work safely. A scheduled refresh later calls this exact same use case, not a second ingestion implementation.

08 / build order

Trust the ledger before optimizing rewards

First usable slice

1. A trustworthy adaptive ledger

Support one bank end to end with Gmail, known-template extraction, adaptive fallback, SQLite, corrections, refresh status, monthly spending, and a basic daily allowance.

Acceptance: a changed-format fixture is extracted correctly; ambiguous fixtures are flagged; replay creates no duplicates; OTPs/declines are not purchases; repayments are not double-counted.

Core product

2. Cards + daily maintenance

Define rules for the user's three cards, then add chat-driven onboarding, sourced drafts, campaign progress, and daily MileLion/official-term checks through the same catalog and publisher.

Acceptance: a card name produces a cited draft or gaps; blog-only changes stay inactive; verified updates obey publication policy and effective dates. Reward examples match hand calculations.

After correctness

3. Coverage + optimization

Statement/CSV reconciliation, more extraction coverage, reward payout confirmation, reminders, optional transaction polling, planned-spend card suggestions, and standalone packaging.

Acceptance: explain recommendations and their assumptions; never encourage unnecessary spending merely to hit a threshold.

Suggestion ranking should use incremental reward value on already-planned spending, remaining caps and conditions, fees, and a user-supplied miles valuation. Avoid claiming an optimal card when key merchant or payment-channel information is missing.

Before implementation

Three inputs that shape the first slice

  1. Personal card/promotion facts: the service should discover public terms itself. Ask the user only for approval/enrollment dates, signup channel, active campaigns, and other personal eligibility facts that public documents cannot establish.
  2. Sanitized Gmail examples: Gmail notification coverage is confirmed. Collect example messages from the three banks to implement and test parsing; note which statement exports are available for reconciliation.
  3. Budget meaning: desired savings/fixed-bill allocation, whether to count expected income, and whether Python/local-browser delivery suits your workflow.

Defaults in this proposal: one user, one machine, SGD reporting, Singapore calendar, read-only Gmail access, conservative budgeting, manual transaction refresh, daily card-news/term checks, policy-gated rule updates, and no automatic bank actions.
